Obsługa błędów

Dwa nurty: panic! i Result.

panic!

Sytuacja bez wyjścia (indeks poza tablicą, nieudana asercja). Wywala program z komunikatem, stack trace domyślnie zwija się — pełny obraz przez RUST_BACKTRACE=1.

Result i propagacja

Błąd spodziewany to wartość Result<T, E>. Najważniejszy nawyk — operator ?: zwraca błąd wyżej albo rozpakowuje sukces. 

use std::{fs, io};

fn wczytaj_pierwsza_linia(sciezka: &str) -> Result<String, io::Error> {
    let tresc = fs::read_to_string(sciezka)?;       // Err? oddaj wyżej
    let linia = tresc.lines().next().unwrap_or("");
    Ok(linia.to_string())
}

// main może zwracać Result — błędy trafią na stderr
fn main() -> Result<(), Box<dyn std::error::Error>> {
    println!("{}", wczytaj_pierwsza_linia("a.txt")?);
    Ok(())
}

panic! czy nie?

  • Przykład, prototyp, test — unwrap/expect dozwolone.
  • Biblioteka — zwracaj Result, nie decyduj za użytkownika.
  • Uszkodzenie stanu (naruszona niezmiennik) — panika ma rację bytu.
  • Rozpakowując Option/Result, expect z opisem mówi więcej niż goły unwrap.

Walidację warto wynosić do typów: konstruktor zwracający Result gwarantuje, że uszkodzony obiekt w ogóle nie powstanie.

Podsumowanie

Spodziewane błędy: Result + ? (propagacja). Awaryjne: panic!. main zwracający Result to wygodny szablon programów. W bibliotekach nie panikujemy bez powodu.

Ćwiczenia

1. Co dokładnie robi ? wewnątrz funkcji zwracającej Result?

Jeśli wartość to Err(e) — natychmiast zwraca to Err z funkcji (po konwersji From::from, jeśli typy błędu się różnią). Przy Ok(v) — zwraca v. Rozwija się to w match.

2. Napisz funkcję parsującą u32 z tekstu, zwracającą własny komunikat błędu.

fn parses(s: &str) -> Result<u32, String> { s.parse::<u32>().map_err(|e| format!("błędna liczba: {s} ({e})")) } — map_err przekształca obcy błąd w nasz typ.

3. Kiedy unwrap() jest akceptowalny w produkcyjnym kodzie?

Gdy wiesz, że błąd nie może nastąpić i da się to obronić komentarzem/asercją (np. Regex::new na stałym wzorcu), w kodzie testowym, albo gdy konsekwencją i tak jest awaria procesu. W bibliotekach lepiej go unikać.
