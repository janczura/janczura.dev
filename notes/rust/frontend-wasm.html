Frontend w Rust: Leptos i WebAssembly

Reaktywność bez wirtualnego DOM, resourcy z Suspense, routing i formy działające bez JavaScriptu.

Cztery prymitywy reaktywne

Leptos nie diffuje drzewa — aktualizuje dokładnie te węzły DOM, które czytały dany sygnał. Wybór prymitywu to decyzja o kosztach: 

let (query, set_query) = signal(String::new());  // getter + setter oddzielnie
let filters = RwSignal::new(BookFilter::default()); // oba w jednym, do przekazywania
let trimmed = Memo::new(move |_| query.get().trim().to_lowercase()); // cache z wynikami
let is_searching = move || !trimmed.get().is_empty(); // zwykłe domknięcie też jest reaktywne
  • signal — rozdzielone getter/setter: dziecku dajesz getter bez uprawnienia do zapisu.
  • RwSignal — obie połówki w jednej wartości, wygodne w obrębie komponentu.
  • Memo — cache'uje obliczenie i powiadamia tylko gdy wynik faktycznie się zmienił; dla drogich obliczeń lub wielu odbiorców. Tani pochodny = zwykłe domknięcie, memo płaci własną administracją.

Resource, Suspense, Transition

Resource wiąże signal (lub krotkę sygnałów) z asynchronicznym ładowaczem: zmiana źródła = auto-odświeżenie, brak zmiany = żądanie w ogóle nie leci. Granice widoku opisują stany ładowania i błędu: 

let books = Resource::new(
    move || (trimmed.get(), filters.get()),        // źródło: krotka = każde pole liczy się
    |(search, filters)| async move {
        list_books(BookFilter { search: Some(search), ..filters }).await
    },
);

view! {
    <Suspense fallback=move || view! { <CatalogueSkeleton/> }>
        <ErrorBoundary fallback=|errors| view! { <p class="error">"Nie da rady pobrać."> }>
            {move || books.get().map(|r| r.map(|list| view! { <BookGrid books=list/> }))}
        </ErrorBoundary>
    </Suspense>
}
  • Suspense pokazuje fallback gdy resource wisi; zagnieżdżone granice napełniają się niezależnie.
  • Transition — przy ciągłym edytowaniu (pole wyszukiwania) zachowuje starą treść zamiast mrugać szkieletem przy każdej literze. Wyszukiwarka należy do transition, nie do suspense.
  • ErrorBoundary łapie Resulty, które wyszły błędem — para z Suspense obejmuje każdy wynik zdalnego wywołania.
  • Warianty resource: blocking (SSR czeka — treść dla search engine w pierwszym HTML) i local (tylko przeglądarka, przyjmuje futury bez Send).

Routing

Drzewo tras deklaruje się raz — serwer renderuje z niego pierwszy HTML, router w przeglądarce przejmuje nawigację; dwa światy nie mogą się rozjechać. fallback jest obowiązkowy — compiler każe zdecydować, co wyświetla nieznany adres.

  • Wszystko poza <Routes> (nawigacja, stopka) przeżywa nawigację bez re-renderu.
  • ParentRoute — layout z outlet, dziecko zmienia tylko region.
  • Parametry przez typowaną strukturę #[derive(Params)]; identyfikator jako Option<Uuid> — adres edytuje człowiek, parsowanie nieudane to stan zwykły, nie panic. Param karmi źródło resource'a, więc zmiana id = auto-pobranie, synchronizacja „przez konstrukcję".
  • <A> renderuje prawdziwy <a> (środkowy przycisk, crawlery działają), use_navigate() — sterowanie z kodu po sukcesie operacji.

Komponenty i formy

#[component]
pub fn BookCard(
    #[prop(into)] title: String,      // przyjmie też &str
    #[prop(optional)] cover_url: Option<String>, // można pominąć
    #[prop(default = true)] show_price: bool,
    price_cents: i64,
) -> impl IntoView {
    view! {
        <Show when=move || show_price>   // reaktywny warunek; zwykłe if = statyczny
            <p class="price">{format_money(price_cents)}</p>
        </Show>
    }
}
  • Children — wołany raz (layout); ChildrenFn — klonowalny, gdy renderujesz dzieci wielokrotnie. Typ mówi o intencji.
  • Server functions: #[server] kompiluje jedną funkcję do endpointu na serwerze i typowanego zdalnego wołania w WASM — trasa, kodowanie i dekodowanie generowane; zmiana typu sygnatury psuje obie strony przy kompilacji. Nie dla API publicznego — tam kontrakt projektuje się świadomie.
  • Actions: ServerAction + ActionForm = formularz HTML, który normalnie POST-uje gdy WASM nie wstał (progresywne ulepszenie) i przez JS gdy wstał. Sygnał pending blokuje przycisk (podwójne kliknięcia), a warunkowy UPDATE w bazie łapie resztę — dwie warstwy, dwie różne przyczyny duplikatów.

Interakcja z przeglądarką

Bezpośrednie API przeglądarki: wasm-bindgen + web-sys z feature'ami na WebSocket itd. Dwie pułapki własne dla WASM:

  • Domknięcie przekazane do JS musi przeżyć rejestrację — forget() wycieka je na zawsze; trzymaj je w StoredValue, a zwolnij w on_cleanup.
  • Router podmienia komponenty bez przeładowania strony — każdy nabyty zasób (socket, timer, subskrypcja) wymaga pariującego zwolnienia w cleanupie, inaczej nawigacje akumulują połączenia.
  • Effect wykonuje się tylko w przeglądarce — bezpieczne na stronie renderowanej wcześniej przez serwer.

Rozmiar bundla

# Cargo.toml — profil tylko dla builda przeglądarkowego
[profile.wasm-release]
inherits = "release"
opt-level = "z"   // rozmiar ponad prędkość — bundl jest na ścieżce krytycznej
lto = true
codegen-units = 1
panic = "abort"    // bez maszynerii unwinding; przeglądarka i tak przeładuje

Mierz na build --release — dev bundle z debuginfo zawyża obraz kilka razy. Trzymanie szacunku: framework dotyka zwykle mniejszości crate'ów projektu (w książkowym przykładzie 2 z 6) — reszta przeżyłaby wymianę frontendu, co jest ceną i zabezpieczeniem architektury z rozdziału o architekturze.

Podsumowanie

Sygnały/memo tworzą graf zależności aktualizujący konkretne węzły DOM. Resource = asynchroniczne ładowanie przypięte do źródła; Suspense/Transition/ ErrorBoundary opisują czekanie i porażkę. Trasy raz, parametry typowane, komponenty przez props z into/optional/default. Server functions i ActionForm dają typed RPC z fallbackiem bez JS. Profil z + LTO na bundle.

Ćwiczenia

1. Pole wyszukiwania umieszczone w zwykłym Suspence mruga szkieletem przy każdym znaku. Czemu i jak to naprawić?

Suspense przy każdym odświeżeniu zasobu cofa się do fallbacku. Transition pokazuje starą treść w trakcie ładowania nowej — dla ciągle edytowanego pola to właściwa granica.

2. Czym Show różni się od if w widoku i kiedy co?

if liczy się raz i produkuje statyczny markup; Show re-ewaluuje warunek reaktywnie i podmienia treść po zmianie sygnału. Warunek zależny od sygnału w if = widok poprawny na pierwszym renderze i głuchy na wszystko potem.

3. Co się stanie z WebSocketem otwartym w komponencie, jeśli nie zarejestrujesz cleanupu?

Nawigacja odejmie komponent, ale socket zostanie otwarty. Po kilku powrotach do strony przeglądarka dobije do limitu połączeń i nowe nie wystartują. Zasób nabyty = zasób zwolniony w on_cleanup.
