Miniserver HTTP

Wszystko naraz: gniazda, wątki, kolejkowanie zadań i zamykanie strumieni.

Cel

Serwer HTTP bez zewnętrznych bibliotek: słucha na porcie, przyjmuje połączenia, czyta żądanie i odpowiada HTML-em. Obsługuje wiele zapytań jednocześnie — przez pulę workerów i kolejkę zadań.

Szkielet

use std::net::{TcpListener, TcpStream};
use std::io::{Read, Write};

let sluchacz = TcpListener::bind("127.0.0.1:7878").unwrap();

for polaczenie in sluchacz.incoming() {
    let mut strumien = polaczenie.unwrap();
    let mut buf = [0; 1024];
    let n = strumien.read(&mut buf).unwrap();
    println!("pytanie: {:?}", &buf[..n]);

    strumien.write_all(b"HTTP/1.1 200 OK\r\n\r\n<h1>czesc</h1>").unwrap();
}

incoming() to iterator — czeka na kolejne połączenia. Zapis odpowiedzi to surowe bajty zgodne z protokołem: linia statusu, pusta linia, ciało.

Wiele żądań naraz

Obsługa w pętli głównej wykonuje zapytania szeregowo. Poprawka: na każde połączenie osobny wątek. Skala? Źle — wątek na żądanie kosztuje pamięć i kontekst przy większym ruchu. Złoty środek: pula N workerów i kanał zadań. 

let (nadawca, odbiornik) = mpsc::channel();

// N workerów czeka na zadania
for _ in 0..4 {
    let nadawca = nadawca.clone();
    thread::spawn(move || {
        while let Ok(strumien) = odbiornik.recv() {
            obslug(strumien);
        }
    });
}

// pętla główna tylko wrzuca połączenia do kolejki
for polaczenie in sluchacz.incoming() {
    nadawca.send(polaczenie.unwrap()).unwrap();
}

Pułapki na końcu

  • Klient, który nie czyta odpowiedzi, blokuje workera na zapisie — jeden zły interesariusz spowalnia kolejkę. Praktyczne wyjście: buforowanie/timeouty albo osobne połączenia.
  • Praca w pętli głównej (parsowanie, logika) powinna być tania; drogie rzeczy — do workera.
  • Blokada strumienia po write: bez flush/zamknięcia klient może czekać. Odpowiedź „cała na raz, potem cisza".

Podsumowanie

Kilkaset linii bez zależności: iterator gniazd, kanał, czterech workerów. Projekt zamyka krąg — własność, cechy, wątki i błędy spotykają się w jednym, działającym programie.

Ćwiczenia

1. Dlaczego „wątek na żądanie" nie skaluje się dobrze?

Każdy wątek to kawał pamięci na stos i koszt utworzenia/planowania. Przy dużym ruchu wątków przybywa szybciej niż rdzeni, a większość czeka na I/O. Pula o stałej liczbie workerów trzyma koszt w ryzach.

2. Co się stanie, jeśli jeden worker utknie na zapisie do wolnego klienta?

Wolne miejsce w kolejce znika — pozostali workerzy i kolejkujący nadawca mogą czekać. Stąd koncepcja timeoutów albo zapisów nieblokujących; w wersji minimum: worker musi w końcu odpuścić strumień.

3. Gdzie w tym serwerze widać regułę własności przy przechowywaniu strumienia?

send(polaczenie) przenosi TcpStream do workera — jeden właściciel na raz, więc nikt inny nie zapisze i nie wyczyści go równolegle. Zamknięcie następuje samo, gdy worker zakończy obsługę (Drop).
