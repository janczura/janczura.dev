REST, GraphQL, OAuth

Interfejs publikowany to kontrakt: wersjonowanie, paginacja kursorowa, limity GraphQL i PKCE.

Kontrakt przeżywa kod

Własny frontend zniesie zmianę, bo deployujecie się razem; mobilka albo partner — nie. Zmiana zgodna to tylko addytywna: nowe opcjonalne pola, nowe endpointy, nowe warianty enuma do zignorowania. Usunięcie, zmiana nazwy, zmiany typu czy nowy wymagany parametr łamią kogoś i trafiają do nowej wersji (.nest("/api/v1", ...)).

  • Typ odpowiedzi żyje w warstwie WWW, nie w domenowym — model domenowy serializowany wprost staje się kontraktem przez wypadek i każdy refactor go zagraża.
  • #[serde(skip_serializing_if = "Option::is_none")] — pola obecne tylko gdy mają wartość; klient nie widzi szumu.

Paginacja kursorowa

Limit bez kursora zmusza klienta do zgadywania, czy coś jeszcze zostało. Licznik total kosztuje drugie zapytanie — sprytniej: fetch limit+1. Nadwyżkowy wiersz = „są następni", po czym go wycinasz. 

#[derive(Serialize)]
pub struct Page<T> {
    pub items: Vec<T>,
    pub next_cursor: Option<String>,
    pub has_more: bool,
}

// limit+1, has_more = len > limit, truncate(limit)

Kursor zachowuje poprawność przy równoległych wstawkach — offset przy każdym nowym wpisie przesuwa się o jeden i klient zobaczy duplikat albo coś ominie. Kotwicą jest ostatni zwrócony element (np. sortowanie po tytule).

ETag i RFC 9457

Katalog zmienia się rzadko, klienci odpytują często: odpowiedź niesie walidator (hash znacznika czasu rekordu — nie serializowanego ciała, bo zmiana typu odpowiedzi nie powinna unieważniać wszystkich cache'y), klient odsyła go w If-None-Match, a Ty oddajesz puste 304. Oszczędzasz transfer i parsowanie, nie samo zapytanie — na to dopiero cache w Redisie.

Błędy interfejsu publicznego w formacie RFC 9457 (application/problem+json): type (trwały identyfikator przeżywający każdą redakcję tytułu), title, status, plus członki rozszerzeń z danymi maszynowo czytalnymi (np. available: 3 zamiast liczby w zdaniu). Klient reaguje programowo, nie parząc angielski.

GraphQL: async-graphql

Klient bierze dokładnie te pola, których potrzebuje. Typy GraphQL to opakowania modeli domenowych (jak w warstwie trwałej — domena bez derivów infrastrukturalnych), co dodatkowo pozwala wystawiać pola obliczane i chować te, które nie powinny ujrzeć świata (stan magazynowy wie konkurencja, klient nie musi): 

pub struct BookNode(pub Book);

#[Object]
impl BookNode {
    async fn price(&self) -> String {   // pole tylko w schemacie: formatowanie centów
        format!("{}.{:02}", self.0.price_cents / 100, self.0.price_cents % 100)
    }
    async fn in_stock(&self) -> bool { self.0.stock > 0 }  // liczba ukryta, boolean widoczny
}

// korzeń złożony z kawałków po areach usług:
#[derive(MergedObject, Default)]
pub struct Query(BookQuery, OrderQuery);
  • Limity obowiązkowe na publicznym schemacie: limit_depth(10) + limit_complexity(200). GraphQL pozwala jednemu żądaniu zażądać wykładniczej pracy przez zagnieżdżenie, które wygląda niewinnie — odrzucić taniej niż wykonać.
  • DataLoader na N+1: dziesięć zamówień po trzy wiersze to 30 lookupów książki; loader zbiera identyfikatory z jednej ścieżki wykonania i pyta raz (deduplikacja + WHERE id = ANY($1) = jeden prepared statement na dowolny rozmiar partii).
  • Eksplorator GraphiQL tylko w dev — wystawiony na produkcji reklamuje cały schemat każdemu.
  • Oba backendy montują schemat identycznym handlerem — schema.execute(req).await.

OAuth2 z GitHubem: PKCE + stan

Delegowanie logowania: nie widzisz hasła, dostajesz kod do wymiany na token. Builder oauth2 v5 pilnuje kompletności typami — exchange przed ustawieniem set_token_uri nie kompiluje się (v4 meldował to dopiero przy pierwszym logowaniu). 

let (challenge, verifier) = PkceCodeChallenge::new_random_sha256();
let (auth_url, csrf) = client
    .authorize_url(CsrfToken::new_random)
    .add_scope(Scope::new("read:user".to_owned()))
    .set_pkce_challenge(challenge)
    .url();

// verifier do Redis, klucz = stan, TTL 10 min — nie do klienta
redis.set_ex(format!("oauth:{csrf}"), verifier.secret(), 600).await?;
  • PKCE: przechwycony kod bez weryfikatora nic nie daje. Stan: callback z nieznaną wartością odrzucasz (CSRF). Oba świeże przy każdym logowaniu.
  • get_del przy odbiorze = jednokrotny odczyt atomowo: replay z historii przeglądarki nie wymieni kodu drugi raz.
  • Client wymieniający token: Policy::none() dla redirects (kredencja nie może powędrować za przekierowaniem w nieznane) i jawny timeout.
  • Prosisz o minimalne scope — tożsamość i e-mail. Szerokie zgody to straszak na consent screenie i większa odpowiedzialność przy wycieku.
  • Wydajesz własny JWT, token dostawcy nie wędruje dalej (daje dostęp poza Twoją aplikacją).
  • ON CONFLICT (email) DO UPDATE = upsert bez wyścigu dwóch równoległych pierwszych logowań; pusty password_hash odcina ścieżkę hasłową takiemu kontu (Argon2 nigdy nie zwraca pustego haszu).

Podsumowanie

Publikujesz kontrakt: wersja w ścieżce, zmiany tylko addytywne, typy odpowiedzi oddzielone od domeny. Kursor z trikiem limit+1, ETag ze znacznika czasu, błędy w problem+json z maszynowymi rozszerzeniami. GraphQL: opakowania, limity głębokości i złożoności, DataLoader na N+1. OAuth: PKCE + jednorazowy stan, minimalne scope'y, własny token na końcu.

Ćwiczenia

1. Klient paginuje offsetem i skarży się na duplikaty. Co się stało?

W trakcie przechodzenia katalogu ktoś wstawił rekord — wszystkie kolejne offsety przesunęły się o jedno. Kursor kotwiczony do ostatnio zwróconego elementu jest na wstawki odporny.

2. Dlaczego ETag liczysz od updated_at, a nie od ciała odpowiedzi?

Hash ciała zmienia się też przy przebudowie odpowiedzi (nowe pole, inna kolejność) i unieważnia cache przy premierze, która danych nie ruszyła. Znacznik czasu rekordu zmienia się dokładnie wtedy, kiedy klient ma prawo zobaczyć coś nowego.

3. Co by było, gdyby callback OAuth odczytywał stan zwykłym GET-em, a potem usuwał go osobno?

Okno między odczytem a kasowaniem pozwala na replay: dwa szybkie żądania z tym samym kodem przeszłyby oba. get_del wykonuje odczyt+usuwanie atomowo, więc drugi klient dostaje pusto i odmowę.
