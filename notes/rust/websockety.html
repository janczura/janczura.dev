WebSocket i aktualizacje na żywo

Serwer odzywa się pierwszy: eventy domenowe, broadcast, tickety do handshake i backoff.

Zdarzenia domenowe

Event opisuje co się stało, nie co zrobić. Typ mieszka w domenie razem z modelami (zero infrastruktury) i musi być identycznie rozumiany po obu stronach — wewnętrznie tagowany serde daje dyskryminator w JSON-ie: 

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "event", rename_all = "snake_case")]
pub enum StoreEvent {
    StockChanged { book_id: Uuid, remaining: i32 },
    OrderAdvanced { order_id: Uuid, status: OrderStatus },
}

Nowy wariant = zmiana addytywna: starszy klient rozpozna i pominie to, czego nie zna. Fanout przez tokio::sync::broadcast — każdy odbiorca dostaje każdą wiadomość, publikujący pisze raz niezależnie od liczby nasłuchujących.

  • send() błęduje tylko gdy zero subskrybentów (nikt nie ma otwartego sklepu) — to normalność, log na trace, bez alarmu.
  • Publikuj po commit, nie przed: rollback unieważniłby zmianę, o której przeglądarki już by usłyszały.

Upgrade połączenia

WebSocket zaczyna się jako zwykły HTTP z nagłówkiem upgrade. Handler Axum zwraca odpowiedź zanim popłynie pierwszy event — dalsza rozmowa dzieje się poza cyklem requestu, poza timeoutami requestów. 

pub async fn ws_handler(ws: WebSocketUpgrade, State(state): State<AppState>) -> Response {
    ws.on_upgrade(move |socket| pump_events(socket, state))
}

async fn pump_events(mut socket: WebSocket, state: AppState) {
    let mut events = state.events.subscribe();
    loop {
        tokio::select! {
            incoming = socket.recv() => { // czytamy nawet bez treści — zamknięcie klienta widać dopiero tu
                if koniec(incoming) { break; } }
            event = events.recv() => match event {
                Ok(e)  => { if socket.send(Message::Text(e.to_text())).await.is_err() { break; } }
                Err(RecvError::Lagged(n)) => { // klient odbiega — nie odrabiamy, każemy odświeżyć
                    socket.send(resync_msg()).await; }
                Err(RecvError::Closed) => break,
            },
        }
    }
}
  • Axum 0.8: ramka tekstowa przyjmuje Utf8Bytes, nie String — potknięcie przy przenoszeniu starszych przykładów, mniej kopiowania w zamian.
  • Aktywny ping odpowiadania: Axum robi pong wewnętrznie; w Actix trzeba odpisać samodzielnie, bo zniecierpliwiony proxy rozerwie milczący koniec.

Actix: sesja jako osobny task

actix_ws::handle zwraca trzy rzeczy naraz: odpowiedź (do natychmiastowego zwrotu), uchwyt sesji do pisania i strumień ramek wejściowych. Pętlę odpala się jako task na tym samym workerze — zgodnie z modelem arbitera sesja nigdy nie zmienia wątku, więc jej stan nie musi być współdzielalny (zero blokad).

Strona przeglądarki

Socket przez web-sys; hook zamyka najnowszy event w sygnale, który czytają komponenty. Rzeczywistość mobilna wymaga polityki reconnectu: backoff wykładniczy + jitter — bez losowości wszyscy rozłączeni tym samym incydentem wróciliby w tej samej sekundzie i położyły odradzający się serwer powtórnie. Licznik prób resetuje się po dłuższej stabilności (chwilowy zanik sieci ≠ problem trwały). 

fn next_delay(attempt: u32) -> Duration {
    let base = 500u64.saturating_mul(1 << attempt.min(6));
    let capped = base.min(30_000);
    let jitter = (js_sys::Math::random() * capped as f64 * 0.3) as u64;
    Duration::from_millis(capped - jitter)
}

Handshake: bilet zamiast tokenu

Konstruktor WebSocketu w przeglądarce przyjmie URL i nic więcej — nagłówka Authorization nie da się dołożyć. Long token w query ląduje w logach proxy i historii. Wyjście: krótki, jednorazowy bilet — REST-owy endpoint z logowaniem wrzuca UUID do Redis z TTL 30 s, handshake konsumuje go przez get_del.

Zasada: kredyt długoterminowy należy do nagłówka, który nie trafia do URL-a; wartość jednorazowa może wędrować gdzie wygodnie.

Backpressure i SSE vs WebSocket

  • Broadcast ma bufor ograniczony: wolny odbiorca gubi nadwyżki (zamiast rosnąć w pamięć bez limitu), a Ty dostajesz Lagged(n). Odpowiedź: instrukcja resynchronizacji (jedno odświeżenie = poprawny stan), nie odtwarzanie zagubionego (per-klientowa historia = z powrotem nieograniczona pamięć).
  • Rozmiar bufora to realna regulacja: za mały gubi przy drobnym zastoju, za duży je pamięć (pojemność × rozmiar × subskrybenci). Ustalać pomiarem.
  • Uczciwe pytanie: czy w ogóle WebSocket? Ruch jednokierunkowy (serwer → przeglądarka) to także Server-Sent Events: auto-reconnect bez Twojego backoffu, ciasteczka bez biletów, multipleksacja HTTP/2, przyjaźniejszy dla proxy. Socket wygrywa dla ruchu dwustronnego, binarnego i bardzo szybkiego. Wybieraj mechanizm od kształtu ruchu, nie od efektowności.

Podsumowanie

Event = dane z dyskryminatorem w domenie; broadcast fan-out, publikacja po commicie. select! na obu kierunkach zamknięcia; Lagged → resync. Actix: sesja jako task per worker, pongi ręcznie. Reconnect z jitterem, handshake przez jednorazowy bilet, a przy ruchu w jedną stronę rozważ SSE.

Ćwiczenia

1. Dlaczego po rollbacku transakcji nie wolno było opublikować eventu przed nią?

Przeglądarki dostałyby informację o zmianie, która nigdy nie nastąpiła — rollback kasuje wszystko w transakcji, a event wysłany wcześniej już żyje własnym życiem. Fakt, który broadcastuje, musi być trwały: publikujemy po commit.

2. Co odczytujesz z socketu, skoro i tak ignorujesz treść?

Informację o zamknięciu. Wynik z recv() (None / błąd / ramka Close) to jedyny sygnał, że klient zniknął — bez czekania na recv pętla pracowałaby wiecznie dla martwego połączenia.

3. Twoja aplikacja tylko wypycha statusy do przeglądarki. Wybierz mechanizm i uzasadnij.

SSE: jedyny kierunek ruchu, więc dwustronność socketu jest płatna, a nie użyta. Dostajesz reconnect, ciasteczka i HTTP/2 gratis. Socket zostaw na moment, gdy klient zacznie realnie nadawać.
