Równoległość

Wątki, kanały i współdzielony stan — bez data race'ów, ale nie bez wysiłku.

Wątek z domknięciem

use std::thread;

let uchwyt = thread::spawn(|| {
    println!("pracuję w tle");
});
uchwyt.join().unwrap();

Wątek zwykle żyje krócej niż main, więc domknięcie musi przejąć dane na własność — stąd move: zamyka zmienne „do środka", a nie pożycza referencje, które mogłyby przeżyć zapożyczającego.

join czeka na koniec wątku i zwraca Result: Err, gdy wątek się zbuntował (panika). Wątek można też „odpalić i zapomnieć" — main skończy się bez czekania.

Kanały — komunikacja przez wysyłkę

use std::sync::mpsc;

let (nadawca, odbiornik) = mpsc::channel();
let h = thread::spawn(move || {
    for i in 0..5 { nadawca.send(i).unwrap(); }
});
for otrzymane in odbiornik { println!("odebrane {otrzymane}"); }
h.join().unwrap();
  • mpsc: wielu nadawców, jeden odbiorca. Wszystkie końcówki wysyłające trzeba pozbyć się (klonować przez clone albo zużyć), bo pętla po odbiorca czeka do ostatniej — to najczęstsza pułapka.
  • Wysłanie wartości przenosi jej własność — data race z definicji niemożliwy: w jednym miejscu tylko jeden właściciel.
  • Są też warianty: sync_channel (ograniczony bufor, wysyłka blokuje), a dla jednego nadawcy i wielu odbiorców mpsc nie istnieje — tam z reguły wchodzi Mutex.

Współdzielony stan: Mutex i Arc

use std::sync::{Arc, Mutex};
use std::thread;

let licznik = Arc::new(Mutex::new(0));
let mut uchwyty = vec![];

for _ in 0..3 {
    let licznik = Arc::clone(&licznik);
    uchwyty.push(thread::spawn(move || {
        *licznik.lock().unwrap() += 1;
    }));
}
for h in uchwyty { h.join().unwrap(); }
  • Mutex<T> to RefCell dla wielu wątków: lock() blokuje i daje „strażnika" (guard), który zwalnia blokadę przy upuszczeniu. Panika wewnątrz sekcji krytycznej nie zostawia zamka otwartego — lock() zwraca Result, bo zamek może być „zatruty".
  • Arc (atomowe Rc) dzieli własność między wątki — klonuje się licznik, nie dane. Bez niego Mutex nie ma nawet czego trzymać wspólnie: każdy wątek dostałby własną kopię.
  • Typowy wzorzec: Arc<Mutex<T>>. Trzyma się blokadę jak najkrócej — nie wolno trzymać jej przez join ani przy zagnieżdżonych zamkach, bo łatwo o zakleszczenie.

Send i Sync

Dwie markerowe cechy, dzięki którym kompilator wyrzuca błędy współdzielenia z góry:

  • Send: wartość można przenieść do innego wątku (przez spawn lub kanał).
  • Sync: wartość można bezpiecznie pożyczać z wielu wątków (&T wysyłalne).
  • Rc nie jest ani jednym, ani drugim — jego licznik nie jest atomowy, dlatego współdzielone wątkowo typy używają Arc. RefCell też nie jest Sync (jego licznik pożyczki też nie).
  • Większość typów jest automatycznie Send/Sync; to wyjątki (wskaźniki surowe, Rc) trzeba sobie przypomnieć.

Podsumowanie

Rust nie eliminuje wyścigów składniową magią — eliminuje je typem: wysyłka przenosi własność, a współdzielony stan zamyka się w Arc<Mutex<T>>. Data race nie jest tu wypadkiem przy pracy, tylko klasą błędów nie do skonstruowania.

Ćwiczenia

1. Dlaczego pętla for v in odbiornik wisi w nieskończoność, choć wątek wysłał już wszystko?

Odbiornik czeka, aż wszystkie końcówki nadawcze zostaną zniszczone. Jeśli oryginał nadawcy wciąż żyje w main (albo sklonowana wersja w innym wątku), kanał jest nadal otwarty. Rozwiązanie: puścić nadawcę (drop) albo nie kopiować go bez potrzeby.

2. Co grozi trzymaniem lock() przez długi czas lub przy zagnieżdżonych zamkach?

Przy długim trzymaniu: inni czekają, współbieżność znika. Przy zagnieżdżeniu dwóch zamków w odwrotnej kolejności w dwóch wątkach — zakleszczenie (deadlock), bo oba wątki trzymają jeden zamek i czekają na drugi.

3. Dlaczego sam Mutex<T> nie wystarczy do współdzielenia go między wątkami?

Bez przeniesienia własności żaden wątek go nie użyczy — clone Mutexa kopiuje dane, nie współdzieli. Trzeba owijek z udostępnianiem własności: Arc (wielowątkowo). Rc też dałoby współdzielenie, ale jego niestatyczny licznik nie jest wysyłalny między wątkami.
