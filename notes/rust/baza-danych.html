Baza danych: SQLx i PostgreSQL

Migracje, pool, zapytania sprawdzane przy kompilacji, transakcje i Argon2.

Migracje odwracalne

sqlx migrate add -r nazwa tworzy parę plików: w górę i w dół. Pół „w dół" uzupełniamy odwracając kolejność operacji (najpierw znika to, co zależne). Migracja nieodwracalna cicho odbiera jedyną bezpieczną drogę powrotu przy wpadce na produkcji.

  • Reguły w schemacie przeżywają każdy refactor wyżej: CHECK (stock >= 0) i UNIQUE powstrzymają nawet wadliwe zapytanie.
  • sqlx::migrate!() wkompilowuje pliki migracji w binarkę — kontener jedzie z własną historią schematu, bez plików obok. Migrator bierze blokadę doradczą, więc kilka replik startujących naraz nie wyściga się.

Zapytania sprawdzane przy kompilacji

Makra sqlx::query! / query_as! / query_scalar! łączą się z żywą bazą w trakcie budowania i weryfikują SQL wobec realnego schematu: literówka w kolumnie, zły typ albo zła liczba parametrów to błąd kompilacji, nie niespodzianka dla odwiedzającego. Budowa po zmianie schematu bez migracji failuje — i słusznie, to mechanizm działa, nie usterka.

Build bez bazy (CI, kontener): cargo sqlx prepare --workspace zapisuje metadane do katalogu .sqlx, który commitujemy; budowanie z SQLX_OFFLINE=true sprawdza wobec cache'u. Nawyk: zmieniłeś zapytanie — regeneruj metadane, inaczej dziwny błąd budowy. 

let books = sqlx::query_as!(
    Book,
    r#"
    SELECT id, isbn, title FROM books
    WHERE ($1::TEXT IS NULL OR author = $1)        // opcjonalny filtr: NULL = „dowolny"
      AND (NOT $2::BOOLEAN OR stock > 0)
    ORDER BY title LIMIT $3 OFFSET $4
    "#,
    filter.author, filter.in_stock_only,
    filter.limit.clamp(1, 100), filter.offset.max(0),
).fetch_all(&self.pool).await.map_err(storage)?;
  • One prepared statement na wszystkie kombinacje filtrów, plan wykonania w bazie się reuse'uje; parametr wiązany nigdy nie jest interpretowany jako SQL (brak injection).
  • clamp na limicie — klient prosi o cały katalog w jednej odpowiedzi i dostaje sufit; format walidują ekstraktory, wielkość tu.

Pool: granice ważniejsze niż rozmiar

PgPoolOptions::new()
    .max_connections(20)
    .acquire_timeout(Duration::from_secs(5))  // kluczowe!
    .idle_timeout(Duration::from_secs(600))
    .connect(database_url).await?

Bez acquire_timeout żądanie przy wyczerpanej puli czeka w nieskończoność i kolejka rośnie, aż aplikacja padnie wszystkim naraz; limit zamienia to w szybki błąd, który mapowanie błędów już obsługuje. „Więcej" nie znaczy „lepiej": każde połączenie to proces backendowy w PostgreSQL — przegrany pool przenosi kolejkę z aplikacji do serwera. Klony PgPool są darmowe (wskaźnik do wspólnego zestawu) — wiele serwisów, jedna pula.

Transakcje i wyścigi

Zarezerwuj magazyn i zapisz zamówienie — albo oba, albo żaden. Najważniejszy wzorzec rozdziału: warunkowy UPDATE wykonuje decrement i sprawdzenie dostępności w jednej operacji, więc rząd jest blokowany na czas trwania i drugi klient widzi już zmniejszony stan: 

let mut tx = self.pool.begin().await?;

let remaining: Option<i32> = sqlx::query_scalar!(
    "UPDATE books SET stock = stock - $1 WHERE id = $2 AND stock >= $1 RETURNING stock",
    quantity, book_id,
).fetch_optional(&mut *tx).await?;   // None = brak magazynu, zwracamy błąd
  • Osobne „przeczytaj, potem zdecyduj" otwiera okno, w którym dwa zamówienia widzą ten sam stan i oba przechodzą — sprzedaż na minusie gotowy.
  • ? albo panic porzuca uchwyt transakcji bez commitu — SQLx robi rollback przy dropie, żadna ścieżka nie zostawia otwartej transakcji.
  • Sprawdzenie reguły cyklu życia (status: Paid → Packed) z SELECT ... FOR UPDATE: zablokuj rząd, potem oceń — blokada i reguła razem, bo żadna z osobna nie zatrzyma podwójnego przejścia.
  • Adnotacje makr przy własnych typach: AS "status: DbOrderStatus" w SELECT, DbOrderStatus::from(x) as DbOrderStatus w parametrze.

Enum domenowy vs enum bazodanowy

Kuszące: przykleić #[derive(sqlx::Type)] do typu domenowego. Odrzucamy — domena kompiluje się do WASM, gdzie sterownik bazy nie ma sensu. Osobny crate warstwy trwałej z typem lustrzanym i konwersjami From w obie strony; wyczerpujący match oznacza, że nowy wariant po którejkolwiek stronie psuje build i wymusza migrację, zamiast ciszej rozjechać się w runtime'cie. Analogicznie konwersja sqlx::Error → DomainError to zwykła funkcja helper (nie impl From — reguła osieroconej zaciągnęłaby sqlx do domeny): 

pub(crate) fn account_error(err: sqlx::Error) -> DomainError {
    if let sqlx::Error::Database(db) = &err {
        if db.code().as_deref() == Some("23505") {   // naruszenie UNIQUE
            return DomainError::DuplicateEmail;
        }
    }
    storage(err)
}

Argon2 i spawn_blocking

Hasło w bazie nigdy nie występuje w formie odwracalnej. Argon2 celowo jest wolny i pożera pamięć — a to pułapka na runtime'cie async: zajmuje wątek dziesiątki milisekund bez oddawania sterowania, kilka jednoczesnych logowania zatrymuje niepowiązane żądania. Ratunek: 

let valid = tokio::task::spawn_blocking(move || {
    Argon2::default().verify_password(&password, &parsed).is_ok()
}).await?;
  • Reguła kciuka: nieprzerywana praca CPU ponad ~100 mikrosekund (haszowanie, kompresja, parsowanie obrazu) — na pulę blokującą.
  • Sól generowana dla każdego hasła i zapisana w wyniku razem z parametrami — te same hasła dają różne rekordy, a parametry można zaostrzać bez unieważniania starych.
  • Brak konta i złe hasło zwracają ten sam błąd — endpoint logowania nie jest katalogiem użytkowników.

Podsumowanie

Migracje odwracalne i reguły w schemacie; SQL sprawdzany przy kompilacji (offline przez commitnięte .sqlx). Pool z jawnym acquire_timeout, klony darmowe. Warunkowy UPDATE i FOR UPDATE zamykają wyścigi; rollback przy dropie. Enumy i błędy sterownika tłumaczy crate warstwy trwałej, nie domena. Argon2 przez spawn_blocking.

Ćwiczenia

1. Zmieniłeś zapytanie i CI melduje błąd o braku zapytania w cache'u. Co robisz i dlaczego tak?

cargo sqlx prepare i commit nowego .sqlx. Build offline weryfikuje makra wobec zapisanych metadanych — po zmianie SQL cache jest nieaktualny i trzeba go odświeżyć, bo budowanie nie ma dostępu do żywej bazy.

2. Dlaczego sam warunek WHERE stock >= $1 w UPDATE załatwia wyścig?

Ponieważ odczyt, porównanie i zapis dzieją się w jednej operacji na zablokowanym rzędzie. Druga transakcja nie widzi stanu z przed decrementu — dopasowuje mniej wierszy albo czeka na zwolnienie blokady, i po odblokowaniu dostaje None.

3. Co grozi pulowi o 200 połączeniach przy dwóch replikach?

PostgreSQL ma domyślnie ~100 połączeń i płaci procesem backendowym za każde. 2×200 przekracza sufit — kolejkowanie przenosi się do bazy, a administracyjne sesje mogą się nie zmieścić. Rozmiar puli liczy się z iloczynu RPS × czas trzymania, nie „na oko".
