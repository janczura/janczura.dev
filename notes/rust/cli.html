Program CLI od kuchni

Od argumentów do biblioteki — typowa ewolucja projektu.

Argumenty i plik

use std::{env, fs};

let args: Vec<String> = env::args().collect();
let (szukaj, plik) = (&args[1], &args[2]);
let tresc = fs::read_to_string(plik)?;   // czyta cały plik do Stringa

Argument 0 to nazwa programu — prawdziwe parametry zaczynają się od [1].

Podział odpowiedzialności

  1. main — zbiera argumenty, wywołuje logikę, drukuje wynik. Mało kodu, dużo błędów dopuszczalnych.
  2. Logika w bibliotece (src/lib.rs) — przyjmuje &str, zwraca Result, nic nie drukuje. Idealna pod testy.
pub fn znajdz<'a>(szukane: &str, tresc: &'a str) -> Vec<&'a str> {
    tresc.lines().filter(|l| l.contains(szukane)).collect()
}

Reszta ekosystemu CLI

  • Zmienne środowiskowe: env::var("KLUCZ") → Result; np. flaga wielkości liter.
  • Błędy na stderr: eprintln!; dane na stdout — wtedy prog > plik nie łapie komunikatów.
  • TDD: najpierw test czerwony (asercja o oczekiwanym wyniku), potem kod go przechodzący.

Podsumowanie

env::args(), fs::read_to_string, logika poza main i jako biblioteka z Result. eprintln! dla błędów, testy naprzód dla nowej funkcjonalności.

Ćwiczenia

1. Jak poprawnie poinformować o złej liczbie argumentów?

Jeśli args.len() < 3 — wypisz użycie na stderr (eprintln!), zwróć Err albo zakończ z niezerowym kodem wyjścia. Dzięki temu prog > out nie zapełnia pliku komunikatem błędu.

2. Dlaczego logika wyszukiwania powinna przyjmować treść jako parametr, a nie czytać plik sama?

Czysta funkcja (&str na wejściu) jest testowalna bez systemu plików i łatwa do złożenia w większy potok. Wejścia/wyjścia zostają przy main.

3. Dodaj wyszukiwanie nieczułe na wielkość liter (z testem).

Test: assert_eq!(znajdz_case_insensitive("aLa", "Ala ma ALA").len(), 2). Implementacja: porównuj l.to_lowercase().contains(&szukane.to_lowercase()).
