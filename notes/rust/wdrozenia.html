Kontener i CI/CD

Obraz wieloetapowy z cache'em zależności, probe'y, które nie mylą degradacji z awarią, pipeline na tagach.

Obraz wieloetapowy

Build potrzebuje całego toolchaina (~1,5 GB), runtime prawie niczego (<100 MB). Etap kompiluje, do końcowego obrazu jedzie tylko binarka i assety: 

FROM rust:slim AS builder
WORKDIR /app
COPY . .
ENV SQLX_OFFLINE=true          # weryfikacja zapytań z .sqlx, baza niepotrzebna
RUN cargo leptos build --release

FROM debian:bookworm-slim AS runtime
RUN apt-get install -y ca-certificates \
    && useradd --system --uid 10001 libro   # outbound TLS wymaga korzeni!
COPY --from=builder /app/target/release/server /usr/local/bin/
USER 10001
CMD ["/usr/local/bin/server"]
  • ca-certificates — bez nich każde wychodzące HTTPS (GitHub, OpenLibrary) pada dopiero w produkcji.
  • Numeryczny uid: Kubernetes egzekwuje runAsNonRoot tylko gdy zna id z góry. Skompromitowany proces bez przywilejów to mniejszy łup po ucieczce z kontenera.
  • readOnlyRootFilesystem — aplikacja nic nie pisze na dysk (logi na stdout, stan w bazie/Redis), więc blokada zapisu nic nie kosztuje, a zamyka jedno wejście atakującemu.
  • rust-toolchain.toml działa też w budującym obrazie — rustup honoruje plik ze skopiowanego źródła.

Cache zależności: cargo-chef

Warstwa z COPY . . unieważnia cache przy każdej zmianie w kodzie — a zależności kompilują się minuty i zmieniają się raz na tydzień. Chef rozcina to na pół: planner zapisuje przepis (same zależności) do recipe.json, etap cook kompiluje zależności z przepisu zanim pozna źródła. Docker cache'uje drogą warstwę względem manifestu, nie kodu. Efekt w książce: ~4 min → ~40 s przy zmianie tylko aplikacji.

Deployment i probe'y

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1            // startuje nowy, czeka na gotowość, potem zdejmuje stary
    maxUnavailable: 0       // = rollout niewidoczny dla ruchu

Dwa endpointy, dwa różne pytania — mylenie ich płaci katastrofą:

  • /livez (liveness): process odpowiada i basta. Gdyby sprawdzał bazę, awaria bazy zbiłaby probe na wszystkich replikach, Kubernetes pozabijałby wszystkie pody, restarty nic by nie naprawiły — sklep leży zamiast być degradowany.
  • /readyz (readiness): pyta o pulę (z timeoutem) — niedołężna instancja przestaje dostawać ruch i wraca w sekundę po zdrowiu bazy.
  • startupProbe kupuje czas na start (np. migracje), nim liveness zacznie sądzić proces wciąż przygotowujący się.

Zamykanie bez gubienia żądań

Sygnał terminacji ma dokończyć otwarte requesty, nie przesiec je w połowie zapisu: 

axum::serve(listener, app)
    .with_graceful_shutdown(shutdown_signal())  // SIGTERM / ctrl-c
    .await?;

Subtelność, która gubi niejedno staranne wdrożenie: klaster wysyła sygnał i usuwa instancję z endpointów jednocześnie, a propagacja usunięcia przez węzły jest asynchroniczna — proces przestaje słuchać, gdy część proxy jeszcze w niego pisze. Łata: preStop sleep 5. Okres łaski musi przekraczać pauzę plus najdłuższy legalny request (timeout layer) — za krótki tnie robotę w trakcie.

Pipeline na tagach

Release wyzwalany tagiem v*.*.*, nie commitem: nikt nie wydaje przez wypadek, a obraz nosi tag = commit, więc każda uruchomiona instancja jest trace'owalna. Zmienne latest tę własność niszczy — dwie instancje ściągnięte w różnych momentach mogą biec różnym kodem pod tą samą etykietą. 

# bramka — każdy krok przewraca build, obraz nie powstaje
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
sqlx migrate run && cargo sqlx prepare --workspace --check   # dryf metadanych zapytań
cargo nextest run
cargo audit && cargo deny check
  • Te same komendy co taski w edytorze — fail lokalny = fail pipeline'owy, bez „u mnie działa".
  • Deploy = kubectl set image + rollout status --timeout=5m: czekamy na gotowość zamiast zakładać sukces; rollout, który nie wstaje, świeci czerwienią, a nie „udaje, że poszedł".
  • Rollback: kubectl rollout undo — ale wraca kod, schemat zostaje gdzie stał. Dlatego migracje odwracalne i zmiany addektywne wdrażane przed kodem, który ich używa.

Podsumowanie

Dwa etapy obrazu, chef za cache zależności, SQLX_OFFLINE i non-root z numerem. Liveness = process, readiness = baza; startup na migracje. Graceful shutdown plus preStop sleep na propagację endpointów. Pipeline na tagu, bramka fmt/clippy/ sqlx-check/nextest/audit, deploy czekający na readiness, rollback przez undo przy odwracalnych migracjach.

Ćwiczenia

1. Build w kontenerie failuje na makrach sqlx, choć baza działa lokalnie. Czego brakuje?

SQLX_OFFLINE=true plus commitnięty katalog .sqlx — w obrazie nie ma bazy do weryfikacji na żywo, więc makra muszą czytać zapisane metadane. To ten sam mechanizm, który obiecał rozdział o bazie.

2. Awaria bazy, wszystkie readyz padają. Co robi klaster i dlaczego to lepsze niż liveness z pytaniem do bazy?

Instancje zostają żywe, tylko wypinane z ruchu; po powrocie bazy są od razu gotowe. Liveness z bazą pozabijałby wszystkie pody jednocześnie, restart nic by nie naprawił, a degradacja zamieniłaby się w przerwę.

3. Dlaczego grace period 45 s, skoro „wystarczy 15"?

Okres łaski musi pomieścić preStop sleep (5 s, na propagację usunięcia endpointów) plus najdłuższy legalny request (15 s, timeout layer) z zapasem — za krótka wartość obcina pracę już rozpoczętą dokładnie wtedy, gdy najbardziej szkodzi.
