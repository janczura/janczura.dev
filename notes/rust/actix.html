Serwer WWW: Actix Web

Runtime per worker, guardy, ResponseError — drugi framework na tej samej domenie.

Model wykonania: arbiter na worker

Tokio (Axum) ma jedną wielowątkową pulę work-stealing i taski migrują między wątkami. Actix uruchamia kilka niezależnych jednowątkowych runtime'ów (arbiter) — po jednym na workera — a połączenie przyjęte przez workera żyje na nim do końca. Futura nigdy nie zmienia wątku, więc Actix nie wymaga granicy Send od handlerów.

  • Bezcenne przy bibliotekach !Send (bufory wewnętrzne, parsery): pod Axum Mutex albo konstruowanie od nowa przy każdym żądaniu; pod Actix — jedna instancja per worker, bez blokady.
  • Cechy domenowe z Send Actix akceptuje bez problemu (surowszą granicę łyka bezboleśnie).
  • Liczbę workerów ustawia HttpServer::workers(); w kontenerze z limitem CPU warto jawnie.

Stan: fabryka liczy się per worker

Domknięcie fabryki App wykonuje się raz na workera — najczęstszy defekt w Actix to stan zbudowany w środku (pula połączeń mnoży się przez liczbę workerów, licznik sumuje tylko część ruchu). Stan dzielony buduje się przed fabryką i klonuje przez web::Data (w środku Arc): 

let state = web::Data::new(AppState::new().await); // jedno miejsce, shared

HttpServer::new(move || {   // wywołanie per worker!
    App::new()
        .app_data(state.clone())                                // ten sam Arc
        .app_data(PerWorkerCache { recent: RefCell::new(Vec::new()) }) // kopia na workera
        .wrap(Logger::default())
        .configure(register_api)
})
.bind(("0.0.0.0", 3000))?
.run().await

Ekstraktory Actix (web::Data, web::Query, web::Path, web::Json) rozwiązuje jedna cecha FromRequest — kolejność parametrów jest dowolna (nawet ciało w środku), w przeciwieństwie do Axum.

Routing: scope, resource, route

Trzy zagnieżdżone poziomy: scope (prefiks + własne middleware), resource (wzorzec ścieżki, wiele metod), route (metoda + handler). Nazwane zasoby dają generowanie URL-i wstecz — linki nie są duplikowane, więc zmiana ścieżki nie zostawia martwych odwołań. 

pub fn register_api(cfg: &mut ServiceConfig) {
    cfg.service(
        web::scope("/api")
            .service(web::resource("/books/{id}")
                .name("book_detail")
                .route(web::get().to(find_book))),
    );
}

// URL generowany z definicji, nie z stringa:
req.url_for("book_detail", [id.to_string()])

ServiceConfig jako osobna funkcja rejestracji skraca fabrykę i pozwala testować routing niezależnie.

Guardy: decyzja przed handlerem

Guard odrzuca lub przyjmuje request na poziomie tabeli tras (nagłówek, host, parametr), łączony przez guard::Any / guard::All. Dwa zasoby o tej samej ścieżce obsługują różne klienty — negocjacja treści nie siedzi w handlerze: 

web::resource("/books")
    .guard(guard::Header("accept", "application/json"))
    .route(web::get().to(list_books)),          // API
web::resource("/books")
    .route(web::get().to(render_book_list_html)), // przeglądarka — trafi tu bez guarda

Własny guard to jedna metoda — wersjonowanie po nagłówku x-api-version: 2 już współistnieje pod jedną ścieżką, dopóki migracja nie dobiegnie końca.

Błędy: ResponseError zamiast IntoResponse

Actix rozdziela kod statusu od ciała: cecha ResponseError (wymaga Display + Debug) ma status_code() i error_response(). Status można odpytać bez budowania odpowiedzi; domyślna implementacja ciała bywa wystarczająca. 

#[derive(Debug)]
pub struct ApiError(pub DomainError);

impl ResponseError for ApiError {
    fn status_code(&self) -> StatusCode {
        match &self.0 { /* te same warianty co w Axum */ }
    }
    fn error_response(&self) -> HttpResponse {
        HttpResponse::build(self.status_code()).json(json!({ "error": msg }))
    }
}

Praktyczna różnica: wiele crate'ów ekosystemu implementuje ResponseError samodzielnie, więc cudzy błąd często konwertuje się bez naszego opakowania; uniwersalny actix_web::Error pozwala miksować rodziny błędów w jednej sygnaturze. Reguła osieroconej implementacji zostaje w obu frameworkach — własnego wrapperka i tak trzeba napisać.

Middleware i porównanie frameworków

  • from_fn(require_auth) — middleware z funkcji; stan przez req.app_data() (ekstraktory jeszcze nie działają). scope(...).wrap(...) chroni całą gałąź drzewa tras, a fallback poza scope dostaje normalne 404.
  • Stan w środku? Para cech Transform (konfiguracja raz per worker) + Service (per request) — np. licznik żądań bez blokady, bo każdy worker ma własną kopię.
  • Gotowa paczka: Compress, NormalizePath, DefaultHeaders, Logger — wszystko jednym wrap.

Wybór: Axum, gdy żyjesz w ekosystemie tower (middleware od load-sheddingu po retry, wspólne z gRPC) i chcesz jednolity stan; Actix, gdy potrzebujesz guardów, generowania URL-i lub trzymasz zależności !Send. Domena nie zależy od wyboru — cały ten rozdział to tylko druga translacja HTTP na te same cechy.

Podsumowanie

Actix = arbiter per worker, więc bez Send i z instancjami per worker (RefCell dozwolony). Fabryka App liczy się per worker — dzielony stan tylko sprzed fabryki przez web::Data. Routing scope/resource/route + nazwy + guardy. Błędy przez ResponseError ze statusem oddzielonym od ciała.

Ćwiczenia

1. Zbudowałeś PgPool wewnątrz domknięcia fabryki Actix. Ile pul masz przy 8 workerach i czego to dowód?

Osiem — fabryka wykonuje się per worker, więc pool otwiera się osiem razy, a licznik „żądań obsłużonych" widzi tylko 1/8 ruchu. Compiler obu pomyłek nie widzi; dzielony stan buduje się przed fabryką.

2. Dlaczego handler Actix może trzymać RefCell, a handler Axum nie?

Bo futura Actix nigdy nie zmienia wątku (arbiter jednowątkowy) — RefCell (!Send) jest bezpieczny. W Tokio task może migrować, więc compiler zażąda Send, a RefCell go nie spełnia.

3. Jak zmiana ścieżki /books/{id} nie zostawia martwych linków w szablonach?

Zasobowi nadano nazwę, a linki generuje url_for("book_detail", [id]) — jedna definicja, wszystkie odwołania wywodzą się z niej. Przy Axum trzeba by zaktualizować każdy string z osobna.
