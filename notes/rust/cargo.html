Cargo głębiej

Profile, dokumentacja, workspace'y — życie poza hello world.

Profile kompilacji

Domyślnie istnieją dev i release; w Cargo.toml można stroić optymalizację, LTO, panic=abort, a nawet dopisywać własne (np. profiling).

Publikacja crate'u

  • Dokumentacja w komentarzach /// (Markdown + blok ``` jako test przykładu — cargo test go kompiluje!).
  • pub use w lib.rs buduje wygodne API: użytkownik widzi krazik::Punkt, nie wewnętrzną strukturę modułów.
  • cargo publish po założeniu konta na crates.io; cargo package robi paczkę i sprawdza, co w niej siedzi. Nowa wersja = zmiana numeru w manifeście.

Workspace

Kilka pakietów, jeden wspólny Cargo.toml z sekcją [workspace] i wspólne target/ — mniejsze dyski i wspólne lockowanie zależności: 

[workspace]
members = ["krazik_core", "krazik_kli"]
resolver = "2"

Reszta wygód

  • cargo install nazwa — budowa i instalacja programu z crates.io.
  • Własne komendy: wykonywalny plik cargo-nazwa w PATH staje się cargo nazwa.
  • cargo doc --open, cargo bench, cargo clippy (linty, instalacja raz).

Podsumowanie

Profile sterują kompromisem czas kompilacji / szybkość. Dokumentacja to obywatel pierwszej klasy (a przykłady są testami). Workspace scala monorepo, crates.io dzieli kod ze światem.

Ćwiczenia

1. Co się stanie, jeśli w komentarzu /// zamieścisz blok kodu z błędem?

cargo test (dok testów) nie skompiluje przykładu i zgłosi błąd. To zaleta: przykłady w dokumentacji nigdy nie rozjeżdżają się z API.

2. Po co workspace, skoro pakiety mogą być osobno?

Wspólny katalog build (mniej kopiowania artefaktów), jeden Cargo.lock dla całego zestawu i wzajemne zależności pakietów rozwiązują się lokalnie. Idealne, gdy biblioteka i jej binarka/klienty żyją w jednym repo.

3. Jak ukryć wewnętrzną implementację, udostępniając jedno API?

Prywatne moduły (mod wnetrze; bez pub) + re-eksport: pub use wnetrze::Punkt; w lib.rs. Ścieżka publiczna jest stabilna niezależnie od przemeblowania w środku.
