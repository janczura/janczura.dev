Funkcje zaawansowane

unsafe, cechy głębiej, nowe typy, makra — warsztat wyżej w łańcuchu pokarmowym.

unsafe Rust

Blok unsafe nie wyłącza sprawdzania typów — włącza pięć nadużyć, za które odpowiadasz ręcznie:

  • dereferencjacja wskaźnika surowego (*const T / *mut T)
  • wywołanie niezbezpiecznej funkcji (np. FFI)
  • implementacja niezbezpiecznej cechy
  • dotknięcie mutowalnej zmiennej globalnej (static mut)
  • (historycznie) dopasowanie wzorca na unii
let wartosc = 42;
let wskaznik = &wartosc as const i32;   // wskaźnik surowy: pożyczka nie pilnowana
unsafe { println!("{}", *wskaznik); }    // "na pewno wskaznik jest ważny" — Twoja wina

unsafe fn w przeszłości sam implikował unsafe dla ciała; nowe edycje wymagają jawnego bloku. Konwencja: ciało funkcji pozostaje bezpieczne, a dokumentacja # Safety mówi, jakich zobowiązań musi dotrzymać wołający.

Cechy głębiej

  • Typy skojarzone: type Output; w cesze — jeden typ wynikowy na implementację. Bez tego generyczny parametr cechy pozwalałby na dwie implementacje „równoległe" do tego samego typu.
  • Przeciążanie operatorów: cechy z std::ops (Add, Index, Deref…) — wdrażasz semantykę, nie nazwy.
  • Cechy bazowe: A: B w nagłówku cechy — wymaga, by implementujący miał już B; albo dyn A + B dla składanych obiektów.
  • Super-cecha vs asocjowana cecha: super-cecha = „musi być", asocjowana = „zwraca/czyni".

Nowe typy i aliasy

// alias: ta sama wartość, inna nazwa — bez dodatkowej ochrony
type Jednostka = u32;

// newtype: nowa tożsamość — kompilator pilnuje, by nie pomylić metrów ze stopami
struct Metry(u32);
struct Stopy(u32);

Newtype (krotka-jednoelementowa) to najtańsza domena: brak konwersji przez pomyłkę, własne implementacje cech, zerowy koszt (reprezentacja identyczna jak w środku).

Funkcje i domknięcia głębiej

  • Trzy sposoby przyjmowania cechy domknięcia: Fn (pożycza), FnMut (mutuje pożyczoną), FnOnce (konsumuje — dozwolone raz).
  • Wymagaj jak najmniej (Fn), zwracaj konkretnie; w API publicznym: impl Fn dla prostoty, Box<dyn Fn> albo jawna nazwa typu, gdy funkcja jest przechowywana.

Makra

  • Rozwinięcie makra zachodzi przed kompilacją — makro widzi tokeny, nie typy. Może wygenerować kod, którego nie da się napisać generykiem (np. vec!, println! z argumentami różnego typu).
  • Deklaratywne (macro_rules!) — reguły wzorców tokenowych; proceduralne — funkcje produkujące tokeny (atrybuty, derive).
  • Cena: gorsze komunikaty błędów i czytelność — dlatego najpierw funkcja, potem generyk, makro na końcu.

Podsumowanie

unsafe to mały obszar, gdzie ufasz sobie zamiast compilerowi. Cechy z typami skojarzonymi, newtype'y i makra to narzędzia, które poszerzają język bez ruszania jego rdzenia — każde z własnym, konkretnym zastosowaniem.

Ćwiczenia

1. Dlaczego preferować typ skojarzony nad parametr cechy?

Parametr dopuszcza wiele implementacji tej samej cechy dla jednego typu (trzeba doprecyzowywać ::<..>), a typ skojarzony wymusza jedną — zwykle o to chodzi (np. jeden typ wartości zwracanej iteratora). Krótsze sygnatury, mniej adnotacji.

2. Co daje newtype struct Metry(u32), czego nie da alias?

Nowy, odrębny typ: funkcja oczekująca Metry nie przyjmie Stopy ani surowego u32 bez jawnej konwersji. Alias to tylko przydomek — podmienialny w 100%, bez żadnej ochrony.

3. Dlaczego makro dostaje gorzej sformułowane błędy niż funkcja?

Ekspanduje tokeny przed type checkingiem: błąd widzi dopiero rozwinięty kod, a ścieżka do oryginału ginie w rozwinięciu. Poza tym makro nie zna typów argumentów, więc semantyczne pomyłki łapie późno.
