Testy automatyczne

Test wbudowany w język — bez zewnętrznych frameworków.

Pisanie

fn dlugosc(s: &str) -> usize { s.chars().count() }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn liczy_znaki() {
        assert_eq!(dlugosc("zażółć"), 6);
    }

    #[test]
    #[should_panic]
    fn indeks_poza_koncem() {
        let v = vec![1];
        let _ = v[5];
    }
}
  • assert!, assert_eq!, assert_ne! — atrybut #[should_panic] dla awarii.
  • Test może zwracać Result<(), Box<dyn Error>> i używać ?.
  • #[cfg(test)] — moduł istnieje tylko przy cargo test.

Uruchamianie

cargo test                     // wszystkie testy
cargo test liczy               // filtr po nazwie
cargo test -- --test-threads=1 // bez równoległości
cargo test -- --show-output    // pokaż println! z testu
cargo test -- --ignored        // tylko pominięte (#[ignore])

Domyślnie testy lecą równolegle — używaj osobnych zasobów, jeśli test coś globalnego rusza.

Struktura

  • Jednostkowe — w tym samym pliku, w module tests; widzą kod prywatny.
  • Integracyjne — w katalogu tests/ obok src/; każdy plik to osobny crate korzystający z API biblioteki. Cargo kompiluje je automatycznie.

Podsumowanie

Atrybut #[test] plus assert_* — zero konfiguracji. Filtry nazw, #[ignore], osobne miejsce na testy integracyjne przez API publiczne.

Ćwiczenia

1. Po co use super::*; w module testowym?

Testy mieszkają w zagnieżdżonym module tests — super wskazuje na kod testowany, a * wciąga wszystko do zasięgu. Testy widzą też elementy prywatne rodzica, bo są wewnątrz tego samego pliku/modułu.

2. Oznacz test wymagający sieci jako drogi i uruchom tylko go.

#[ignore] przy funkcji; potem cargo test -- --ignored. Dzięki temu szybka pętla cargo test nie czeka na wolne przypadki.

3. Czego NIE testuje katalog tests/ wprost?

Elementów prywatnych crate'u — każdy plik w tests/ to osobny crate, więc dostęp ma tylko do rzeczy oznaczonych pub. Logika wewnętrzna zostaje testom jednostkowym.
