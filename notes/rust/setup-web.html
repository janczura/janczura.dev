Projekt aplikacji WWW

Wersja a edycja, pinowanie narzędzi, workspace i usługodawcy w Dockerze — fundament powtarzalnego buildu.

Wersja a edycja

Dwie rzeczy, które się myli: wersja (kompilator — nowe wydanie co 6 tygodni, wstecznie zgodne) i edycja (dialekt języka deklarowany per crate w Cargo.toml — pozwala języku łamać zgodność bez dzielenia ekosystemu). Crate na jednej edycji linkuje z crate'em na drugiej bez tarcia, więc edycja nigdy nie ogranicza doboru zależności. Edycja 2024 (stabilna od 1.85) m.in.: ostrzejsze czasy życia wyrażeń końcowych, #[unsafe(no_mangle)], std::env::set_var jako unsafe, oraz impl Trait w zwracanej wartości przechwytujący domyślnie wszystkie lifetime'y w zasięgu.

Pinowanie: rust-toolchain.toml

Zamiast „najnowszego Rusta" — plik przy korzeniu projektu, który rustup czyta automatycznie. Klonowanie repozytorium daje wtedy identyczny kompilator, linter i cele kompilacji bez żadnej ręcznej konfiguracji. To najtańsza eliminacja błędów „u mnie działa". 

# rust-toolchain.toml — rustup sam pobierze to, co tu wpisano
[toolchain]
channel = "1.85.0"
components = ["rustfmt", "clippy", "rust-analyzer"]
targets = ["wasm32-unknown-unknown"]  // cel dla przeglądarki
  • wasm32-unknown-unknown — 32-bitowy WebAssembly bez vendor OS; potrzebny, gdy frontend kompiluje się do WASM.
  • rustup target list --installed — kontrolka, co faktycznie jest zainstalowane.
  • Prezentery binarek: cargo-binstall (ściąga gotowe binarki zamiast godzinnej kompilacji), przez niego cargo-leptos, cargo-nextest, sqlx-cli, cargo-audit, cargo-deny.

Manifest workspace

Wersje zależności deklaruje się raz w sekcji workspace, a członkowie je dziedziczą — dwa crate'y nigdy nie różnią się o wersję wspólnego package'u. Kluczowa para pól: rust-version + resolver = "3" (włączany przez edycję 2024) — Cargo nie wybierze zależności wymagającej nowszego kompilatora niż nasz, tylko cofnie się do kompatybilnego wydania. Projekt buduje się dalej, gdy ekosystem podnosi wymagania. 

[workspace]
members = ["app", "domain", "frontend", "server-axum"]
resolver = "3"

[workspace.package]
edition = "2024"
rust-version = "1.85"

[workspace.dependencies]
axum = "0.8"
tokio = { version = "1", features = ["full"] }
sqlx = { version = "0.8", features = ["runtime-tokio-rustls", "postgres", "macros"] }

// w crate'cie członkowskim:
[dependencies]
axum = { workspace = true }
  • Cargo.lock commitujemy — zamienia „cokolwiek Cargo dziś dobierze" w „dokładnie te wersje". Dokładnie tak samo jak pin narzędzia, tylko dla zależności.
  • Nazwy binarek i paczek rozwiązują się po nazwie package'u, nie po katalogu — zmiana nazwy crate'u wymaga aktualizacji wszystkich odwołań.

Usługodawcy w kontenerach

PostgreSQL i Redis startują przez docker compose up -d — wersja obrazu pinuje baza tak samo mocno, jak rust-toolchain.toml pinuje kompilator. Aplikacja czyta adresy ze zmiennych środowiska (.env: DATABASE_URL, REDIS_URL, RUST_LOG), nigdy z zaszytych stringów. Wolumeny nazwane przeżywają restarty; docker compose down -v czysci dane w sekundy.

Bramka jakości

Ten sam zestaw komend lokalnie (jako taski edytora) i w CI — dzięki temu błędy wychodzą przed pushem, a nie po nim: 

cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo nextest run

W edytorze warto ustawić check.command = clippy (linter na bieżąco, nie tylko cargo check) oraz allFeatures = true, gdy kod bywa strzeżony feature flags — inaczej edytor analizuje tylko włączoną gałąź.

Podsumowanie

Pinujemy wszystko, co się da: kompilator (rust-toolchain.toml), zależności (commitnięty Cargo.lock + resolver 3 z rust-version), wersje baz (obrazy Dockera). Edycja to dialekt, wersja to kompilator — i jedno, i drugie zapisane w repo. Narzędzia instalowane przez cargo-binstall, bramka fmt/clippy/nextest jednakowa lokalnie i w CI.

Ćwiczenia

1. Czy crate na edycji 2021 może zależeć od crate'u na edycji 2024?

Tak. Edycja to sprawa wewnętrzna danego crate'u (wpis w jego Cargo.toml); linkowanie między edycjami działa bez tarcia. Wybór edycji nie ogranicza listy zależności.

2. Co robi combination rust-version + resolver = "3", której nie ma resolver 2?

Szuka wersji zależności kompatybilnych z zadeklarowanym minimalnym kompilatorem. Jeśli nowy release package'u podnosi wymagania ponad nasz kompilator, Cargo wybierze starszy, działający release — zamiast zbudować projekt, który się nie kompiluje.

3. Dlaczego brak commitniętego Cargo.lock to problem w aplikacji (nie w bibliotece)?

Aplikacja ma jedno drzewo zależności i jeden artefakt — bez locka każdy build (i każdy kontener) może dostać inne wersje przejściowe i inne zachowanie. Biblioteka odwrotnie: lock ignorują jej konsumenci, tam liczy się zakres z manifestu.
